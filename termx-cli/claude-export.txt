  1. Local hub 的端口策略

   hub 之后这个 cmux 结构保留，逻辑不变。

  决策点：单端口（HTTP + ICE-TCP
  共用）还是双端口（分开）？单端口对用户友好（只开一个防火墙端口），推荐单端口。

  ---
  2. Local hub 的 Web Controller 替代

  Cloud mode 下 hub 用 controlclient 调云端 Web Controller 来验证 app
  certificate。Local hub 没有云端 Web Controller，但你要求"同等认证强度"。

  这意味着 local hub 需要一个本地信任策略：只有已经配对的 app certificate
  才被接受。具体有两种实现：

  方案 A：local hub 信任 machine 自签发的 app certificate
  - machine 在 pairing 时颁发 app certificate（用 machine key 签名）
  - local hub 只需验证签名来自本机 machine key，不需要云端
  - 适合"机器自主控制谁能连"的场景

  方案 B：local hub 也调云端 Web Controller 验证
  - local hub 仍然联网验证 app certificate
  - 完全等同 cloud hub 的认证强度
  - 缺点：断网时 local mode 失效

  你要的是哪种？我倾向方案 A——local mode 本来就是离线/局域网场景，machine key
  自签就足够有认证强度，同时保留离线能力。

  ---
  3. Both 模式的 agent 双注册

  Both 模式需要 agent 同时注册到两个 hub（本地 + 云端）。现在
  agent/runtime.Manager 只管理单个 hub 连接。

  两个路径：

  方案 A：两个独立 Manager 实例
  local runtime: Manager → local hub (127.0.0.1:18888)
  cloud runtime: Manager → cloud hub (hub.termx.io)
  简单，代码改动小，但 agent 在两个 hub 里各有一个 session，pairing
  需要分开处理。

  方案 B：Manager 支持多 hub 注册
  一个 Manager，维护多个 hub 连接，统一 session/inventory。
  复杂，改动大，现阶段不划算。

  推荐方案 A。Service 里维护两个 localRuntime 和
  cloudRuntime，各自独立生命周期。

  ---
  4. ICE-TCP only 还是 ICE-TCP preferred？

  "WebRTC over TCP" 在 LAN 场景下有两个语义：

  - TCP only：ice config 只广播 TCP candidate，不用 UDP
  - TCP preferred：先尝试 TCP，UDP 作为 fallback

  LAN 内 TCP 延迟完全可接受，且穿透性更好（很多公司网络封了 UDP）。但如果同一个

      for _, s := range stats {

          }
